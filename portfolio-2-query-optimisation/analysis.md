**Case study:** PayEdge Digital Bank
**Environment:** PostgreSQL 17 on a local machine, queried through IntelliJ

---

## 1. Test setup

| Item | Value |
|---|---|
| Test data | 5,005 customers, 5,007 accounts, 500,010 transactions (generated by `seed_volume.sql`) |
| `transactions` table size | 52 MB (6,667 pages of 8 KB) |
| Statistics | Refreshed with `ANALYZE` before the baseline and again after the indexes were created |
| Measurement | `EXPLAIN (ANALYZE, BUFFERS)`, each test run twice, with the second run recorded |
| Baseline | No indexes on `transactions` beyond the primary key and the UNIQUE index on `reference` |

### Indexes created

```sql
CREATE INDEX idx_txn_from_account ON transactions (from_account_id);
CREATE INDEX idx_txn_to_account   ON transactions (to_account_id);
CREATE INDEX idx_txn_status_date  ON transactions (status, transaction_date DESC);
CREATE INDEX idx_accounts_customer ON accounts (customer_id);
```

## 3. Interpretation

### 3.1 Why the planner changed its choice

PostgreSQL uses a cost-based optimiser. For each query it estimates the cost of every candidate plan from table statistics (row counts, value distributions, and available indexes) and picks the cheapest.

Before the indexes existed, a sequential scan was the only way to find the rows. Test A, for example, removed about 166,640 rows per worker to return 90, and the planner's cost estimate was about 10,281. After the indexes existed, a cheaper path became available, and the estimated cost dropped to about 366, so the planner switched.

The planner's estimates were close to reality in every test (for example, it estimated 99 rows for Test A against 90 actual rows, and 4,006 against 4,160 for Test B), which shows the statistics were accurate. A wrong choice usually comes from stale statistics, so `ANALYZE` after bulk loading matters.

### 3.2 Why the three tests improved by different amounts

- **Test A (about 62x)** is highly selective. It returns 90 of 500,010 rows (0.02%), so the index finds them almost directly. Only 93 pages were read, compared with 6,667.
- **Test C (about 1,250x)** gained the most because of the `OR` condition. A sequential scan had to read every row and then sort. The planner used a `BitmapOr`, combining the two account indexes so that only about 195 rows were fetched before sorting. This is the strongest argument for indexing both `from_account_id` and `to_account_id`.
- **Test B (about 34x)** gained the least, even though it is still a clear win. It returns 4,154 rows (about 0.8% of the table), yet the plan still read 3,121 pages, roughly half of the table's 6,667 pages. In the seeded data, failed transactions are scattered randomly through the table, so the matching rows sit on a large share of the pages. The index avoided examining every row, but it could not avoid visiting many pages. This shows that an index helps in proportion to how selective the query is, and also depends on how the data is physically laid out.

### 3.3 Why a bitmap scan, not a plain index scan

All three "after" plans use a bitmap scan. The planner first builds a bitmap of matching row locations from the index, sorts them by page, and then reads each page once. This is efficient when matching rows are scattered across many pages, as they are in the randomly seeded data. In Test A, `Heap Blocks: exact=90` shows that the 90 matching rows sat on 90 different pages.

### 3.4 Small differences in the results

- Test B returned 4,160 rows before and 4,154 after. The filter depends on `NOW()`, which moved between the two runs, so a few transactions at the 30-day boundary dropped out of the window. The data was not changed.
- All reads came from memory (`shared hit`, no `read`), so every timing above is a warm-cache figure. On a cold cache the sequential scans would be slower still, so the real-world gap is likely larger than measured here.

## 4. Trade-offs of indexing

| Benefit | Cost |
|---|---|
| Large speed-ups on selective reads (up to about 1,250x in this test) | The three new indexes added **22 MB** on a 52 MB table |
| Far fewer pages read, which reduces I/O and CPU | Every `INSERT`, `UPDATE` and `DELETE` on `transactions` must also maintain each index |
| Supports joins and sorting efficiently | Indexes that go unused still cost storage and write time |
| | The planner has more plans to consider, so planning can take slightly longer |

The write overhead was **not benchmarked** in this portfolio, so it is stated here as a known cost, not a measured one. For a transaction table that is written constantly, this matters: each new index slows every transfer slightly. That is why the indexes were chosen to match actual query patterns (account lookups and status-by-date reports) and not added to every column.

Indexes are not always chosen either. For a query that returns a large share of the table, a sequential scan is usually cheaper, and the planner will correctly ignore the index.

---

## 5. Conclusion

Indexing the columns used for filtering and joining turned three full-table scans into targeted index lookups. Execution time fell by about 34x to about 1,250x, and pages read fell by up to about 72x, for a storage cost of 22 MB. The results confirm that query performance depends on three things working together: well-chosen indexes, accurate statistics, and the planner's cost-based comparison of plans.
